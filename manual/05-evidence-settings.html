Chapter 10

Evidence and target lifecycle

REA is built around evidence rather than prose. A finding is only as good as the record behind it, and a session is only as clean as the targets it closes. This chapter covers both halves of that discipline.

10.1 Evidence identifiers

When a REA tool returns a durable fact, it returns an evidence record with an identifier of the form ev_ followed by 64 hexadecimal characters — a SHA-256 digest.

PropertyMeaning
Content-derivedThe identifier is computed from the record content. The same facts produce the same ID; different facts produce a different ID.
QuotableYou can paste an ID into a report, a ticket or another session. It identifies the record, not a file path or a moment in time.
ComparableBundle comparison is defined in terms of record identity. Two bundles that share an ID share the exact record.
Verifiablerea evidence-import validates every ID and canonical manifest before merging.

REA Studio extracts identifiers from assistant text and tool output with a strict pattern: ev_ plus exactly 64 hexadecimal characters. Truncated identifiers, ellipsised identifiers and invented identifiers are not tracked. This is deliberate — a partial ID is not a reference.

Do not retype evidence IDs

Copy them from the Evidence tab or the transcript chip. A single changed character produces a different, non-existent record, and the bundle validator will reject it.

10.2 Transcript versus evidence

The transcript is a conversation. The evidence registry is the durable record. They serve different purposes:

ArtifactContainsSurvives
Transcript (Markdown save)Messages, tool names, statuses, output excerpts and the evidence IDs that were cited.As long as the file is kept. The IDs are pointers, not records.
Evidence tabThe IDs seen in this session, their first source and time.The current session only.
Evidence bundle (JSON)Complete records with canonical ordering, manifests and residual-unknown history.Permanently, and it can be imported into another session.

A report that cites an ID is only reproducible if the matching bundle was exported. Export before closing the session or the target if the finding matters.

10.3 Bundle operations

The Evidence tab has five controls. Each runs a deterministic REA command in a fresh process and prints the result below the list.

ControlCommandPurpose
Export…rea evidence-export <source> <output> --overwriteCanonicalise an existing bundle into byte-stable ordering. Use it before archiving or signing.
Validate…rea evidence-import <path>Validate every Evidence ID and manifest, then merge. Imported content is data only and is never executed.
Inspect…rea inspect-evidence-bundle {"path":"…"}Read the bundle inventory: record metadata, manifests, unknown history, links.
Compare…rea compare <left> <right>Compare two bundles by record identity. Missing members describe omission, never behavioral equivalence.
Copy all—Copy every tracked ID, one per line.

Inside the agent session, the equivalent MCP tools are export_evidence_bundle, import_evidence_bundle, get_evidence_bundle and compare_bundles. Use the agent when you need the live session's records; use the console commands when you already have a bundle file.

Two evidence stores

The console is a fresh CLI process. It cannot see the records the agent holds in its MCP session. To capture live findings, ask the agent to export a bundle, then inspect that file with the console controls.

10.4 Target lifecycle

A target is an artifact an analysis engine has open. REA tools bind to the active target, and the engine keeps resources (a Ghidra Program, a debugger session, a browser context) until the target is closed.

  1. Open. A tool call with a path — analyze, decompile, capture-*, start_*_session — opens or attaches a target. The Activity tab records it from the tool input fields path, target_path, executable, document, capture and similar keys.
  2. Active. Subsequent calls without a path operate on the open target. This is why one artifact per session is easier to reason about.
  3. Close. close_binary, close_gdb_session, close_frida_session, close_rizin_debug_session, close_build_computer and similar tools release the engine. Evidence and unknown history stay in memory.
  4. Cleanup confirmed. When a close, cleanup, release or detach tool completes, REA Studio removes the matching target row automatically.
UI actionSends this instruction
✕ on a targetClose the target opened from that path, release its analysis/session resources, confirm cleanup, delete nothing.
Close allClose every open target in the session, release resources, confirm cleanup_pending is false, delete nothing.

If REA reports cleanup_pending, a red note appears above the target list. Do not exit the app while it is set: the engine may still hold a file lock or a debugger attachment.

10.5 Target hygiene

  • Close before comparing. A comparison that opens both sides should close both when done, especially when they are large.
  • Do not delete files to force cleanup. Closing releases the handle; deleting the artifact only destroys your own input.
  • Keep snapshots deliberate. close_binary can save a target-bound snapshot. If metadata was edited, the snapshot may be refused until the target is recreated; that refusal protects you from saving an inconsistent image.
  • Export first, then close. Closing does not persist investigation records.

10.6 A defensible evidence workflow

  1. Investigate one artifact in one session.
  2. Ask for evidence IDs to be cited for every material claim.
  3. Check the Evidence tab: the IDs should be complete and few, not dozens of near-duplicates.
  4. Ask the agent to export an evidence bundle to a path inside the workspace.
  5. Validate the bundle with Validate…, then inspect it with Inspect….
  6. Close all targets and confirm cleanup is not pending.
  7. Save the transcript for the narrative, and keep the bundle for the facts.
Chapter 11

Settings, files and shortcuts

11.1 Settings file

Preferences live in one JSON file:

%APPDATA%\REA Studio\settings.json

A typical file after a few sessions:

{
  "workspace": "D:\\REA",
  "model": { "providerID": "anthropic", "modelID": "claude-sonnet-4-5" },
  "agent": "build",
  "recent": [
    { "id": "ses_…", "title": "Triage notepad.exe" }
  ]
}
KeyEffect
workspaceDirectory the agent runs in and the default location for file dialogs. Sessions are scoped to it.
modelProvider and model for new prompts. null means the server default.
agentAgent name for new prompts. null means the server default.
recentSession titles kept for quick identification. Not the transcript itself.

The file is written whenever you change the workspace, model, agent or a session title. If it is missing or unreadable, the app falls back to D:\REA, then your home directory, then the current directory.

Reset to defaults

Close the app, rename settings.json to settings.json.bak, and start again. The app recreates the file on first change. Sessions and evidence are not stored here.

11.2 Workspace

The workspace chip in the header shows the current directory. Click it (or the workspace line in the rail) to pick another folder.

  • Changing the workspace changes the session list: only sessions created for that directory are shown.
  • File and folder pickers start in the workspace.
  • Relative paths in prompts and console commands resolve against it.
  • The setting persists across restarts.

Choose a workspace that is large enough for analysis output. A decompile-everything run can write thousands of files; point output fields at a dedicated subdirectory.

11.5 Environment variables

REA Studio injects mcp.rea.environment into both the OpenCode server and every REA console command. The two variables that matter most:

VariablePoints atChecked by
GHIDRA_INSTALL_DIRA Ghidra 12.1.x installation directory.Health tab, rea doctor, every Ghidra-backed tool.
JAVA_HOMEA JDK 21+ installation.Ghidra startup and the Health tab.

Other provider variables (IDA, JEB, Frida, adb, sigrok, Playwright) are read from the same block or from the process environment. If you add one, restart the app so a new server inherits it.

The app never edits your OpenCode config

It reads the config to locate the REA CLI and to copy the environment. Changes to opencode.jsonc require a restart; the console and the agent both pick up the new values from the new server process.
